# Repository Guidelines

Python Slack bot built on OpenAI's **Responses API** (never Chat Completions). The
design is stateless: Slack is the source of truth, and conversation context is
rebuilt from platform history on demand. See `CLAUDE.md` for the deeper
architecture notes.

## Project Structure & Module Organization
- Entry points: `main.py` (platform selection) and `slackbot.py` (Slack runner).
- Core functionality lives in **packages**, not single modules:
  - `message_processor/` — message pipeline, handlers, tools, participation logic, plus the
    shared pieces it owns: `prompts.py`, `tool_registry.py`, `thread_manager.py`,
    `token_counter.py`, `message_markers.py`, `canvas_content.py`, and `client_contract.py`
    (the platform-agnostic `BaseClient` / `Message` / `Response` contract). Inbound files,
    images and URLs are turned into model input under `message_processor/ingestion/`.
  - `openai_client/` — Responses API wrapper (`api/`, `base.py`, `utilities.py`,
    `mcp_manager.py`)
  - `slack_client/` — Slack transport, `event_handlers/`, `formatting/`, `settings_modal.py`
    (settings modal UX), `markdown_converter.py`
  - `streaming/` — streaming buffer, fence handling, rate limiting, native sink
- Only these stay at the root: `main.py`, `slackbot.py`, `config.py`, `database.py`,
  `logger.py`, `runtime_identity.py` — they are either entry points, or they import upward into
  the feature packages, so no package below `main` can own them.
- `Docs/` holds specs and plans. Runtime-only dirs: `data/` (SQLite), `logs/`.
- Tests split by scope under `tests/unit/` and `tests/integration/`; shared fixtures
  in `tests/conftest.py`. **Test files go in `tests/`, never the repo root.**

## Build, Test, and Development Commands
- `make install` — install the pinned, hashed lockfile (`pip install --require-hashes -r requirements.txt`).
- `make test` — unit suite (`tests/unit`) with terminal + HTML coverage.
- `make test-unit` / `make test-fast` — unit tests, without the coverage run.
- `make test-integration` / `make test-all` — integration scenarios; these hit real APIs.
- `make lint` — `ruff check .` then `mypy .` (each skipped if not installed).
- `make format` — `black .` then `isort .` (each skipped if not installed).
- `make check` — `lint` + `test`.
- `python3 slackbot.py` — launch the Slack bot once the environment is configured.

## Dependencies
- `requirements.in` is the human-edited source of truth; `requirements.txt` is an
  autogenerated lockfile with exact pins + sha256 hashes. **Never hand-edit the lockfile.**
- Add/remove a dep: edit `requirements.in`, run `make lock`, commit both files.
  `make lock-upgrade` refreshes pins within the existing constraints.
- System packages the bot genuinely shells out to (all via
  `message_processor/ingestion/document_handler.py`):
  `poppler-utils` (PDF page rendering), `tesseract-ocr` (OCR of scanned PDFs), and
  `pandoc` (DOCX fallback extraction). All degrade gracefully when absent.

## Coding Style & Naming Conventions
- Python 3.12 (the lockfile is compiled for 3.12). Four-space indent, `snake_case`
  for modules/functions/variables, `PascalCase` for classes.
- Prefer lean, single-responsibility modules; extract helpers into adjacent files
  rather than growing the runners.
- Format with `black` + `isort`, lint with `ruff`, keep type hints passing `mypy`.
- **`make lint` passes with ZERO errors across 298 files, and every commit must leave it that
  way — run it before you commit** (the pre-commit hook runs ruff and mypy too, in under a
  second). 1114 type errors were cleared in one pass to reach zero, so a new one is a real
  signal rather than noise to scroll past.
- Write to the linters' taste as you go: annotate parameters and returns, `Optional[X]` for
  anything defaulting to `None`, no unused imports. Never silence what you could fix —
  `# type: ignore[code]` is a last resort, always with the specific code and a `#` comment
  saying why. Never narrow a type with `assert x is not None` in production code; it changes
  runtime, and `typing.cast` does not.
- Mixin classes take their host contract from `slack_client/_host.py` and
  `message_processor/_host.py` — a typing-only base that is plain `object` at runtime. Read the
  docstring there before adding a mixin or a shared attribute.

## Testing Guidelines
- Name test files `test_*.py` (see `pytest.ini`). Markers: `unit`, `integration`,
  `critical`, `smoke` — `--strict-markers` is on, so register any new marker.
- Unit tests must not touch the network. Integration tests use real API keys from
  `.env` and are opt-in via `make test-integration` / `make test-all`.
- Never start the bot as part of a test run; the maintainer manages the running process.

## Spec workflow (Claude ↔ codex ↔ implementer)

- Working specs and plans co-authored by Claude (orchestrator) and codex live in
  **`Docs/specs/`** (gitignored — they carry internal IDs and live plans). Session
  scratch directories die with the session; anything a later round needs goes here.
- Every implementation task gets a **Markdown spec** in that folder before code is
  written. The spec must map each requirement to a concrete technical design anchored
  in the real code — exact files, functions, config names, schemas, literal grammars —
  so the implementing agent (Opus 5) has **zero room to invent**. If something is
  unspecified, that is a spec gap to send back, never a decision for the implementer.
- **Authorship: Claude (the orchestrator) writes the spec; codex is the adversarial
  sounding board, not the author and not the final say.** Codex findings are input;
  what ships is decided by Claude's rulings and the owner's decisions, recorded in the
  spec. Codex should challenge hard — and expect to be overruled with reasons.
- Numeric limits are never invented: defaults come from existing tuned values or an
  explicit owner decision, and the spec says which.
- Review rounds check the diff **against the spec first** (conformance, point by
  point), then do the general adversarial pass.

## Commit & Pull Request Guidelines
- History uses **plain imperative subjects — no conventional-commit prefixes**
  (e.g. "Fix: forward tool_event_callback through the OpenAIClient wrapper",
  "Expose link previews as ENABLE_LINK_PREVIEWS (default off)"). Match that; do not
  introduce `feat:` / `refactor:` / `docs:`.
- Keep the subject short and imperative; put detail in the body.
- Update `CHANGELOG.md` alongside user-visible changes.
- PRs should state intent and list validation steps (`make test`, `make lint`). There
  is no CI workflow in this repo — only Dependabot — so run the checks locally.

## Configuration & Secrets
- **This repo is PUBLIC.** Never write a real person's name, a real internal channel name, or a
  credential into any file — tests, fixtures, prompts, docs and CHANGELOG included. Scenarios
  reconstructed from real Slack incidents keep the *shape* and lose the identifiers. Test
  speakers come from the fictional cast in `tests/fixtures/people.py`; add a character there
  rather than inventing one at the call site. `make pii` enforces it, and it runs in the suite.
- Copy `.env.example` when onboarding; never commit secrets. Required keys are
  **`OPENAI_API_KEY`**, plus `SLACK_BOT_TOKEN` and `SLACK_APP_TOKEN`. `OPENAI_KEY` is the
  legacy pre-v3 name, still accepted as a fallback so existing deployments keep working
  without editing their `.env`.
- Use `slack_app_manifest.example.yml` as the template for scopes and event
  subscriptions; `slack_app_manifest.yml` is gitignored and environment-specific.
- If `.venv/` exists, activate it before running Python commands:
  `source .venv/bin/activate`.
